\section{Sprint 1}

\subsection{Planificación del Sprint 1}

\subsubsection{Objetivo y fechas}
El Sprint 1 se planificó del 29/09/2026 al 27/10/2026 con el objetivo de entregar la base de una aplicación SaaS con gestión de usuarios, arquitectura en capas, proceso Scrum en DoneTonic, flujo GitHub Flow, integración y despliegue continuos (CI/CD) en Google Cloud Run y Render, y una batería de pruebas automatizadas. El alcance formal, según directriz docente, se limitó a los Hitos 1, 2 y 3 del enunciado \cite{enunciado}.

\subsubsection{Cambio de alcance}
Durante el sprint, el profesor repartió créditos de Google Cloud para educación. Para aprovecharlos se añadió el PBI \textbf{P19} (despliegue continuo en Google Cloud Run) con sus tareas T29 y T30. Render se mantuvo como despliegue alternativo. Este cambio se refleja en el burndown como un incremento temporal de PBIs pendientes (de 1 a 2) antes del cierre final.

\subsubsection{Lo aprendido}
\begin{itemize}
    \item La disciplina de GitHub Flow (rama por tarea, PR, CI obligatorio) garantiza que no se integra código roto, pero exige gestión activa de ramas locales (\texttt{git fetch}, \texttt{branch -f}) para evitar \textit{non-fast-forward}.
    \item El patrón repositorio con inyección de dependencias permitió cambiar de memoria a PostgreSQL sin tocar la lógica de negocio, validando el diseño con las mismas pruebas de contrato.
    \item La revisión frase a frase contra el enunciado (PR \#30) detectó una desviación real (permiso de \texttt{/active} al propio usuario) que los PBIs no habían capturado.
    \item La concentración de 33 commits de trabajo en un solo día (12/10/2026) cumple la estructura incremental pero no la expectativa pedagógica de avance espaciado; conviene documentarlo con transparencia.
    \item Los secretos deben rotarse si se exponen accidentalmente (cadena Neon en chat); la decisión de no rotar queda registrada en pendientes.
\end{itemize}
