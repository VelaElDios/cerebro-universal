\chapter{Descripción de la Aplicación}
\label{cap:descripcion}

Este capítulo detalla la especificación formal, la arquitectura, el diseño técnico y el funcionamiento del sistema software desarrollado en \textit{La Grada Colchonera}, una plataforma SaaS web orientada a la afición rojiblanca construida como proyecto de aficionado sin vinculación formal con el Club Atlético de Madrid. El sistema conjuga un núcleo de servicios web para la gestión de identidades y persistencia con un videojuego web determinista de supervivencia en tiempo real (\textit{survivor}) en pixel art, cuyas mecánicas se analizan monográficamente en el Capítulo~\ref{cap:juego}. A continuación se presentan el catálogo integral de requisitos, la arquitectura general del sistema, las decisiones de diseño adoptadas, el modelo de datos relacional, la especificación de interfaces de la API, los diagramas de secuencia de los flujos principales, el análisis de seguridad, el resumen comparativo de los sprints y el manual de uso del subsistema SaaS.

\section{Arquitectura del sistema}

La solución adopta una arquitectura cliente-servidor distribuida estructurada en capas bien diferenciadas, bajo el principio de inversión de dependencias. El servidor web Express sirve tanto la interfaz estática como las rutas de la API REST bajo el prefijo \texttt{/api}, lo que elimina problemas de origen cruzado (CORS) al compartir el mismo dominio y puerto. La Figura~\ref{fig:capas} ilustra la interacción entre capas y la Tabla~\ref{tab:capas-responsabilidad} desglosa las responsabilidades asumidas por cada una.

\subsection{Decisiones de diseño}
\label{sec:diseno-decisiones}

Cada decisión técnica se fundamentó en la comparativa rigurosa de alternativas según las directrices de la asignatura:
\begin{enumerate}
    \item \textbf{Uso de Express 5 sin frameworks SPA en cliente:} Se prescindió intencionadamente de librerías como React o Vue en favor de JavaScript estándar. Esta decisión elimina la necesidad de procesos de compilación o transpilación en el frontend, permite examinar de forma directa la arquitectura y garantiza que el backend sirva la aplicación en un mismo origen sin lidiar con CORS. Express 5 ofrece propagación automática de errores asíncronos en middlewares \cite{express}.
    \item \textbf{Patrón Repository con doble implementación:} Se diseñaron repositorios en memoria y sobre PostgreSQL que satisfacen exactamente el mismo contrato. Esta abstracción permite ejecutar el sistema y las pruebas unitarias sin dependencias externas de red o base de datos instalada localmente, validando que la lógica no dependa del motor de almacenamiento.
    \item \textbf{Inyección de dependencias manual:} Cada módulo de servicio recibe sus colaboradores (repositorios, servicios criptográficos, clientes de correo y reloj) a través de sus constructores o factorías. Esta técnica facilita la introducción de dobles de prueba (\textit{mocks} y \textit{stubs}) durante los tests automatizados sin alterar el código productivo.
    \item \textbf{Sesiones en servidor frente a tokens en cliente:} Se descartó el almacenamiento de sesiones exclusivamente mediante JWT en el cliente en favor de identificadores de sesión almacenados en PostgreSQL gestionados por \texttt{express-session}. Esto garantiza la invalidación instantánea de credenciales al cerrar sesión o eliminar una cuenta, además de proteger las claves en cookies marcadas con \texttt{httpOnly}.
    \item \textbf{Baja lógica con liberación de identificadores:} La eliminación de cuentas marca el registro como \texttt{status = 'deleted'} conservando la traza histórica y la auditoría. Mediante índices parciales únicos en PostgreSQL, el correo y el mote quedan liberados de inmediato, posibilitando que el mismo usuario vuelva a registrarse con las mismas credenciales si lo desea.
    \item \textbf{Tokens de confirmación firmados mediante HMAC:} En lugar de registrar tokens aleatorios temporales en base de datos, el sistema genera firmas criptográficas HMAC-SHA256 con fecha de caducidad incrustada. El servidor verifica la autenticidad del token mediante su secreto sin necesidad de consultas de almacenamiento ni procesos de purga.
    \item \textbf{Concurrencia optimista en el club:} Cada perfil de juego incluye un campo numérico \texttt{version}. Al realizar operaciones sensibles (contratos de futbolistas o mejoras de atributos), la sentencia SQL condiciona la actualización con \texttt{WHERE version = \$v}. Si dos peticiones simultáneas intentasen gastar el mismo recurso, una de ellas fallará con código HTTP 409 y obligará al cliente a refrescar su estado antes de reintentar.
\end{enumerate}

\section{Diseño detallado}

\subsection{Módulos del backend}

La organización del código del servidor en \texttt{src/} responde a una alta cohesión modular, tal como se sintetiza en la Tabla~\ref{tab:modulos-backend}:
\begin{itemize}
    \item \texttt{server.js}: punto de entrada principal que carga la configuración de entorno, ejecuta el arranque mediante \texttt{bootstrap} y vincula la escucha HTTP al puerto especificado, gestionando el apagado ordenado (\textit{graceful shutdown}) ante señales \texttt{SIGTERM}.
    \item \texttt{bootstrap.js}: orquestador de inicialización que detecta la disponibilidad de base de datos relacional, ejecuta las migraciones SQL pendientes, promociona al administrador por defecto y selecciona el adaptador de mensajería (SMTP o registro en trazas).
    \item \texttt{app.js}: compone la aplicación Express: análisis de JSON, sesión, enrutamiento bajo \texttt{/api} y entrega estática de ficheros desde el directorio \texttt{public/}.
    \item \texttt{config.js} y \texttt{loadConfig.js}: lectura, saneamiento y validación estricta de las variables de entorno del sistema, abortando la ejecución en producción si se detecta la ausencia de secretos obligatorios.
    \item \texttt{logger.js}: generador de trazas estructuradas en formato JSON por línea con niveles de severidad y filtrado automático de secretos (\texttt{[oculto]}).
    \item \texttt{api/index.js}: agregador de controladores REST con middlewares de auditoría (\texttt{requestLogger}), contexto de identidad (\texttt{currentUser}), rutas públicas y protegidas, gestor de errores y captura de recursos inexistentes (404).
    \item \texttt{api/auth.js}: endpoints de registro, autenticación local, confirmación de correo, reenvío de enlaces, inicio de sesión federado con Google OAuth y revocación de sesión.
    \item \texttt{api/users.js}: endpoints de gestión de usuarios reservados a perfiles de administración (\texttt{GET /api/users}, cambios de rol y bajas).
    \item \texttt{api/juego.js}: endpoints protegidos del subsistema del juego para perfiles, inicio y finalización de partidas con validación anti-trampas, contratos, entrenamientos, motes y clasificación comunitaria.
    \item \texttt{services/userService.js}: reglas de negocio de identidades (registro, validación de contraseñas, vinculación OAuth, borrado lógico y protección del último administrador).
    \item \texttt{services/accountConfirmationService.js}: orquestación del ciclo de vida de confirmación de cuentas mediante tokens firmados y plantillas de correo.
    \item \texttt{services/tokenSigner.js}: generación y validación criptográfica de firmas HMAC-SHA256 con control de tiempo de vida.
    \item \texttt{services/passwordHasher.js}: derivación segura de contraseñas mediante \texttt{bcrypt} (coste 10 en producción y 4 en tests unitarios para optimizar velocidad).
    \item \texttt{services/juegoService.js}: lógica centralizada del servidor del juego (perfiles, recompensas, control de tiempos de partida, cálculo de logros y actualización optimista).
    \item \texttt{services/domainPolicy.js}: política de filtrado para la prueba técnica de dominios autorizados (RF-13).
    \item \texttt{services/errors.js}: catálogo de excepciones de negocio tipadas (\texttt{ValidationError}, \texttt{UnauthorizedError}, \texttt{ForbiddenError}, \texttt{AccountPendingError}, \texttt{NotFoundError}, \texttt{ConflictError}, \texttt{ServiceUnavailableError}).
    \item \texttt{repositories/*}: adaptadores de almacenamiento en memoria y relacional para usuarios y juego (\texttt{postgresUserRepository.js}, \texttt{postgresJuegoRepository.js}, etc.).
    \item \texttt{integrations/*}: clientes de infraestructura externa para transporte SMTP con \texttt{nodemailer} y cliente HTTP de Google OAuth 2.0.
    \item \texttt{db/migrate.js} y \texttt{db/migrations/*.sql}: motor secuencial e idempotente de migraciones relacionales versionadas.
\end{itemize}

Las particularidades del diseño de datos incluyen:
\begin{itemize}
    \item \textbf{Tabla \texttt{users}:} Registra la identidad de cada cuenta. El correo se normaliza a minúsculas sin espacios. La migración \texttt{005} introdujo un índice parcial único (\texttt{CREATE UNIQUE INDEX ... WHERE status != 'deleted'}), permitiendo que tras una baja lógica el usuario pueda crear una cuenta nueva con el mismo email. El campo \texttt{password\_hash} admite valores nulos para usuarios federados con Google.
    \item \textbf{Tabla \texttt{session}:} Administrada automáticamente por el paquete \texttt{connect-pg-simple}. Almacena la carga útil serializada de la sesión en base de datos.
    \item \textbf{Tabla \texttt{juego\_perfiles}:} Guarda el estado del club en un campo binario estructurado \texttt{datos} (JSONB), que almacena la plantilla de jugadores desbloqueados, contadores de victorias, puntos de entrenamiento y logros obtenidos. El campo \texttt{version} sustenta el mecanismo de concurrencia optimista.
    \item \textbf{Tabla \texttt{juego\_records}:} Contiene exclusivamente la mejor marca de supervivencia de cada aficionado (criterio de ordenación por mayor tiempo y, en caso de empate, mayor nivel alcanzado), publicando únicamente el mote y avatar para salvaguardar la privacidad.
\end{itemize}

El ciclo de vida de los estados de una cuenta se sintetiza en la Tabla~\ref{tab:estados-cuenta}:
\begin{itemize}
    \item \texttt{pending}: Estado inicial tras el registro local. Requiere verificación obligatoria por correo para transicionar a \texttt{active}.
    \item \texttt{active}: Cuenta plenamente operativa. Se alcanza directamente en registros vía Google OAuth o tras pulsar el enlace de confirmación.
    \item \texttt{deleted}: Estado irreversible tras una baja voluntaria o administrativa. La sesión asociada se invalida en el siguiente ciclo de petición, el usuario deja de figurar en el ranking comunitario y sus credenciales quedan liberadas para eventuales reingresos futuros.

\subsection{Frontend}

La interfaz de usuario se concibió como una aplicación web de una sola página (\textit{Single Page Application}, SPA) basada en JavaScript vanilla y navegación por fragmento de almohadilla (\textit{hash routing}):
\begin{itemize}
    \item \textbf{Enrutador ligero (\texttt{public/js/ui.js}):} Gestiona las transiciones entre rutas: \texttt{\#/} (inicio), \texttt{\#/entrar} (acceso), \texttt{\#/registro} (alta), \texttt{\#/perfil} (mi cuenta), \texttt{\#/jugar} (juego) y \texttt{\#/admin} (panel administrativo), complementado con la vista 404 («Fuera de juego»). Las rutas declaran metadatos de acceso (\textit{solo invitados}, \textit{autenticados} o \textit{administrador}); no obstante, la validación final se impone en el servidor.
    \item \textbf{Módulos de vistas desacoplados (\texttt{ui/vistas/*.js}):} Cada pantalla exporta una función \texttt{montar(raiz, contexto)} y devuelve una rutina de desmontaje que libera escuchadores de eventos para evitar fugas de memoria. Las vistas se importan dinámicamente mediante \texttt{import()}.
    \item \textbf{Cliente de red unificado (\texttt{public/js/api.js}):} Único módulo del frontend autorizado a realizar llamadas de red mediante la API nativa \texttt{fetch}. Configura cabeceras comunes, establece un tiempo de expiración (\textit{timeout}) de 15 segundos con \texttt{AbortController} y traduce fallos en instancias de la clase \texttt{ApiError}. Si detecta una respuesta HTTP 401 en una sesión previamente válida, notifica al enrutador para revertir el estado de la interfaz al modo invitado.
    \item \textbf{Avisos y accesibilidad (\texttt{ui/avisos.js}, \texttt{ui/modal.js}):} Región dinámica configurada con \texttt{aria-live="polite"} y \texttt{role="alert"} para mensajes de error. Las confirmaciones de acciones destructivas se implementan mediante el elemento nativo accesible \texttt{<dialog>}.
    \item \textbf{Tokens de estilo y diseño adaptable (\texttt{public/css/}):} Sistema visual fundamentado en variables CSS (paleta cromática rojiblanca y modo oscuro, radios, tipografía Plus Jakarta Sans). En pantallas móviles, la tabla del panel de administración transmuta dinámicamente a tarjetas individuales.
\end{itemize}
