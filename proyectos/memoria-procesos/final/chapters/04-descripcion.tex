Las fronteras de comunicación entre módulos están rigurosamente delimitadas:
\begin{itemize}
    \item \textbf{Frontera GUI -- Cliente:} La interfaz \texttt{public/js/ui.js} no invoca directamente funciones de red; delega toda interacción en el cliente \texttt{public/js/api.js}.
    \item \textbf{Frontera API -- Lógica:} Los controladores de \texttt{src/api/users.js} y \texttt{src/api/auth.js} procesan peticiones HTTP e invocan los métodos de \texttt{userService}, sin contener reglas de negocio.
    \item \textbf{Frontera Lógica -- Datos:} El servicio \texttt{userService} invoca operaciones definidas en el contrato del repositorio sin conocer si la persistencia es volátil o relacional.
    \item \textbf{Conexión global:} El archivo \texttt{src/app.js} es el único punto donde se inyectan las dependencias entre capas.
\end{itemize}

\subsection{Modelo de datos}

La persistencia relacional en PostgreSQL se articula mediante migraciones SQL versionadas que definen tres tablas principales:
\begin{itemize}
    \item \textbf{\texttt{users}:} Almacena las identidades del sistema. Contiene los campos \texttt{id} (UUID, clave primaria), \texttt{email} (TEXT, único), \texttt{password\_hash} (TEXT, hash bcrypt), \texttt{role} (\texttt{'user'} o \texttt{'admin'}), \texttt{status} (\texttt{'pending'}, \texttt{'active'} o \texttt{'deleted'}), \texttt{auth\_provider} (\texttt{'local'} o \texttt{'google'}), \texttt{created\_at} (TIMESTAMPTZ) y \texttt{deleted\_at} (TIMESTAMPTZ).
    \item \textbf{\texttt{session}:} Estructurada según el estándar de \texttt{connect-pg-simple}, con campos \texttt{sid}, \texttt{sess} (JSON con datos serializados) y \texttt{expire}.
    \item \textbf{\texttt{schema\_migrations}:} Registra los ficheros de migración ejecutados secuencialmente.
\end{itemize}

Un usuario se considera activo en el sistema cuando su atributo \texttt{status} es igual a \texttt{'active'}, lo que certifica que la cuenta no ha sido dada de baja ni permanece pendiente de confirmación.

\subsection{Ciclo de sesión y control de acceso}

El ciclo de vida de la autenticación se apoya en cookies de sesión firmadas:
\begin{enumerate}
    \item El cliente envía credenciales mediante \texttt{POST /api/auth/login}.
    \item La lógica valida la existencia del usuario y compara la contraseña mediante \texttt{bcryptjs}.
    \item Ante el éxito, Express regenera la sesión para evitar ataques de fijación de sesión, asigna el identificador del usuario y guarda el registro en la base de datos relacional.
    \item El servidor emite una cookie \texttt{grada.sid} con directivas \texttt{httpOnly}, \texttt{sameSite=lax} y una caducidad de 7 días.
    \item Al recargar la aplicación, el cliente invoca \texttt{GET /api/auth/me}. Si el usuario hubiera sido eliminado con posterioridad, la sesión queda automáticamente invalidada.
    \item Al solicitar \texttt{POST /api/auth/logout}, la sesión se destruye en la tabla \texttt{session} del servidor y se limpia la cookie del navegador.
\end{enumerate}

\section{Decisiones técnicas y de diseño}

Cada decisión técnica adoptada en el proyecto responde a requisitos funcionales y de seguridad:
\begin{itemize}
    \item \textbf{Node.js 22 y Express 5:} Permite unificar JavaScript en cliente y servidor, aprovechando la captura nativa de excepciones asíncronas en Express 5 \cite{express,nodejs}.
    \item \textbf{Frontend sin framework compilado:} Elimina la necesidad de transpilación, asegura la entrega desde el mismo origen y delimita nítidamente la capa visual (\texttt{ui.js}) de la capa cliente (\texttt{api.js}).
    \item \textbf{Patrón repositorio e inyección de dependencias:} Se implementaron dos repositorios intercambiables (\texttt{memoryUserRepository} y \texttt{postgresUserRepository}) bajo la misma interfaz. Esto posibilitó migrar al almacenamiento relacional sin modificar la lógica de negocio.
    \item \textbf{Baja lógica (\texttt{status = 'deleted'}):} Evita la eliminación física de registros para preservar auditorías y previene que una cuenta dada de baja vuelva a autenticarse.
    \item \textbf{Ofuscación de mensajes de autenticación:} Se devuelve el mismo mensaje ante correos no registrados o contraseñas inválidas, evitando la enumeración de usuarios.
    \item \textbf{Inicialización del primer administrador (\texttt{ensureAdmin}):} Configurado al arrancar mediante \texttt{ADMIN\_EMAIL} y \texttt{ADMIN\_PASSWORD}. Se ejecuta de forma idempotente sin almacenar credenciales en el código fuente.
    \item \textbf{Protección del último administrador:} La lógica impide degradar o eliminar al último administrador, garantizando que el sistema nunca quede huérfano de gestión.
    \item \textbf{Logging estructurado en JSON:} Emisión por salida estándar hacia Cloud Logging, enmascarando contraseñas, secretos y tokens de sesión.
\end{itemize}
